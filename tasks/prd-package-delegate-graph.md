## Maintenance slice: audit cleanup probe becomes injectable (semantics unchanged)

`runProductionAudit` read machine state inline — `ps -axo pid=,command=` counted against
`/agentfs run.*dg-/", plus temp-directory, Herdr-tab and token-file scans — and folded the result
into `ok`. That read is correct for a real audit and untestable as a unit: running with a fake
`Runner` still probed the live host, so the suite's own concurrency decided the outcome. Twenty-four
other test files start AgentFS, so a full-suite run reported one failure from either launch
directory while a serial run reported none, and the file passed on its own.

The read is now `readCleanup()`, passed to `runProductionAudit` as a fourth parameter defaulting
to itself. Production behaviour is identical: a real audit still probes the real machine, and a
non-zero AgentFS count still fails the bundle — pinned by a new assertion that injects a machine
with one live process and requires `ok === false`. Tests that only exercise gate logic inject a
clean snapshot instead of inheriting whatever the host was running. `countAgentFsProcesses` is
exported and tested against synthetic process lists in the style of
`test/support/acpx-cleanup-driver.py`, which already feeds fabricated `ps` output to the
duplicate of this rule in `scripts/production-cleanup-scan.ts`.

Two things deliberately left open. The rule exists twice (`production-audit.ts` and
`production-cleanup-scan.ts`); they agree today, and unifying them changes what an audit measures,
so it needs its own slice. And one concurrent run failed in `acpx-cleanup.test.ts`, which passes
31/31 alone; the same shape of interference is plausible there and was not reproduced in the three
runs after this change, so it is recorded as unconfirmed rather than fixed.

**Confirmed remaining defect 1 — an approval block can be routed as a transient runtime failure.** `acpx` exits with `EXIT_CODES.PERMISSION_DENIED` (5) and emits `PERMISSION_DENIED` / "Permission request denied or cancelled" whenever every permission request in a turn is denied or cancelled (`applyPermissionExitCode` in the installed `acpx/dist/cli.js`, exit-code table in `acpx/dist/live-checkpoint-*.js`). `scripts/acpx-worker.ts` records that only as `processExitCode` and names the block nowhere, and `wait_for_settled_agent()` converts any non-zero exit or non-`completed` terminal into `ACPX worker failed: exit=<code> terminal=<kind>`. The `retry.ts` pattern `\bACPX worker failed\b|terminal[= ]failed` then classifies that string as transient `worker-runtime-failure`, so an environmental block consumes its same-model budget and may advance the frozen chain. `collect` calls `classifyFailure` without the semantic flag, so the existing "semantic verdicts never trigger failover" rule is never consulted on that path, and the worker lane was the only place an approval block became retryable: the provider lane reads assistant error messages through `classifyFailoverError` in `lib/model-failover-native.mjs`, which returns terminal for a denial, so no cross-layer conflict existed to reconcile. The field consequence reproduced: the same authorized command was denied twice before process creation, and a retry of an identical command reproduces an identical denial.

**Confirmed remaining defect 2 — repeated and partial teardown neither converges nor proves anything.** Reproduced against the real `headless_delegate.py` entry point with real disposable attempt directories, credential files, cancel launchers and AgentFS-shaped databases: three successive teardown calls on one already-torn-down attempt each reported failures and never converged, while every `cleanup` invocation printed `{"cleaned": …}` and wrote no `cleanup-*.json` at all. In source, `command_cleanup` never runs the absence audit and skips all teardown work once `attempt_dir` is gone, so a vanished attempt directory ends the attempt with an unverified reason and no evidence; `abort_acpx_attempt` counts already-absent owned resources as failures, which is why a missing cancel launcher surfaces as `ACPX cancel/close error: [Errno 2] No such file or directory …cancel-acpx.sh` and an already-removed credential surfaces as `materialized provider credential is missing` — the exact historical cleanup behaviour recorded in US-003; those already-gone entries are also appended to the real attempt error, polluting `last_error`. `verify_cleanup_absence` asserts `"sessionClosed": True` as a literal inside its own required list and skips its session-file check whenever the attempt-key field is empty, so an empty inventory satisfies the audit.

**Plan:** two serial mechanical repairs, one owner, no new state layer and no new transport. First make the block visible where it is produced and route it where it is decided: record the permission-denied outcome as a named outcome at the worker boundary instead of only an exit code, name the block in the error the launcher raises, and let `retry.ts` reject a block before its transient pattern scan instead of adding a parallel classifier, so an approval block parks for an operator decision and never retries or falls back. Second make teardown converge on evidence: one teardown audit per attempt that reports each registered owned resource as gone, still present or unverifiable; it runs on every cleanup path including a repeat cleanup and a vanished attempt directory, keeps failing closed for a genuine survivor, takes closure from an observed acpx result rather than a literal, retains the original failure text, and names only a credential basename in any emitted reason.
